🏗️ Overview & Architecture

Berkeley DB (BDB) is the storage engine underlying Comdb2. It uses a Write-Ahead Log (WAL) to ensure ACID compliance and enable recovery from crashes.

Core Principles

Write-Ahead Logging (WAL)

Before any data is written to disk, a log record describing the change is written to the log file and flushed to storage. If the system crashes, replay the log to recover uncommitted state.

Physical vs. Logical Logging

Physical logging: Records the byte-level changes to a page (e.g., "page 5, offset 100-200, write N bytes"). Used by Berkeley DB for low-level B-tree structural operations (__bam_split, __db_addrem, etc.). Physical records must be replayed in order and are page-specific.
Logical logging: Records the user-level intent of the operation (e.g., "insert row with key X and value Y", or "create table with columns X, Y, Z"). Comdb2 uses logical records for schema changes (CREATE TABLE, ALTER TABLE, DROP TABLE) wrapped in logical transactions. Logical records can be replayed independently and don't depend on exact page layout — essential for replicants to apply the same operation even with different B-tree structure.

Durability via Checkpoints

A checkpoint marks a stable point in the log where all dirty pages up to that point have been flushed to disk. During recovery, replay only begins from the last checkpoint, not from the start of the log.

Multi-Version Consistency via LSN

Snapshot isolation in Comdb2 is implemented using LSNs. When a read transaction starts, it captures the current LSN as its snapshot point. All data changes logged at LSNs after the snapshot point are invisible to this reader — it sees a consistent historical view of the database as it existed when the snapshot was taken. Concurrent writes produce newer LSN records, but don't affect snapshot-isolated readers.

Log File Structure

┌─────────────────────────────────────┐ │ log.00000001 (Berkeley DB log) │ ├─────────────────────────────────────┤ │ Offset [1][28] → __txn_recycle │ │ Offset [1][72] → __db_debug │ │ Offset [1][132] → __txn_ckp │ │ Offset [1][200] → __db_debug │ │ Offset [1][256] → __fop_create │ │ Offset [1][314] → __fop_write │ │ ... │ │ Offset [1][9999] → __txn_regop_gen │ │ ... │ └─────────────────────────────────────┘ Each record has a header specifying: - Record type (rec: 2011 for checkpoint) - Transaction ID (txnid) - Previous LSN (prevlsn) for chaining

📍 Log Sequence Numbers (LSN)

An LSN is the unique identifier for every log record, expressed as [file_number][byte_offset].

Structure

Format: [file_number][byte_offset]

Example: [1][1274336]

  • file_number: Which log file (1 = log.00000001, 2 = log.00000002, etc.)
  • byte_offset: Byte offset within that file where the record starts

Purpose

  • Chronological ordering: Later operations have higher LSNs. A transaction at LSN [1][5000] happened before one at [1][6000]
  • Transaction chaining: Each record points to its predecessor via prevlsn, forming a linked list backward in time
  • Checkpoint tracking: Checkpoints record ckp_lsn, the LSN of the oldest active (uncommitted) transaction at checkpoint time. All transactions before ckp_lsn are guaranteed committed and durable on disk
  • Recovery starting point: On crash, recovery begins from ckp_lsn, not from the log beginning. This is safe because all transactions before ckp_lsn are already on stable storage
  • Multi-version consistency: Snapshot-isolated reads use LSN as the snapshot point — a read at LSN [1][5000] sees all commits up to that LSN, but no later ones

Example Transaction Chain

Record 1: [1][256] __fop_create (prevlsn [0][0]) ↓ Record 2: [1][314] __fop_write (prevlsn [1][256]) ↓ Record 3: [1][4484] __fop_write (prevlsn [1][314]) ↓ Record 4: [1][8654] __fop_rename (prevlsn [1][4484]) Each record points backward to its predecessor, enabling efficient forward replay during recovery.

📋 Record Types & Operations

The Berkeley DB log contains dozens of record types. Here are the most important for understanding Comdb2:

Transaction Management Records

__txn_ckp (Checkpoint)

Rectype: 2011

Marks a stable point where all dirty pages have been flushed to disk.

  • ckp_lsn: Oldest active transaction's LSN (point to start replay from)
  • last_ckp: Previous checkpoint LSN
  • timestamp: When checkpoint occurred
  • rep_gen: Replication generation (increments on master election)
  • max_utxnid: Highest transaction ID committed so far

__txn_ckp_recovery (Checkpoint During Recovery)

Rectype: 2020

Written when a node recovers and redoes the log. Marks a safe stopping point.

__txn_recycle (Transaction ID Recycle)

Rectype: 2014

After a checkpoint, recycle the transaction ID space (min/max range). Essential for 32-bit txnid wraparound.

__txn_regop_gen (Transaction Commit — Generation Format)

Rectype: 2016

Marks a user transaction commit. Modern format including replication generation.

  • opcode: 1 = commit (abort would be different code)
  • generation: Replication generation at commit time
  • timestamp: Commit timestamp

__txn_regop_gen_endianize (Transaction Commit — Endianized)

Rectype: 2151

Enhanced commit record with endian markers and additional context for cross-architecture replication.

__txn_regop_rowlocks_endianize (Logical Transaction Commit)

Rectype: 2150

Used for schema change transactions. Includes row lock context and logical transaction ID.

  • ltranid: Logical transaction ID (e.g., for schema operations)
  • begin_lsn: Where this logical txn started
  • lflags: Logical flags indicating transaction properties

__txn_child (Child Transaction Link)

Rectype: 2012

When a parent transaction spawns child transactions, records the parent-child relationship.

Data Modification Records

__db_addrem (Add/Remove Record)

Rectype: 3041

This is a PHYSICAL log record. It records a byte-level modification to a B-tree page: adding or removing a record within the page structure (not the whole record bytes, but the metadata for where it lives on the page).

  • opcode: 1 = add record to page, 2 = remove record from page
  • fileid: Which file (table/index) this operation affects
  • pgno: Page number within that file
  • indx: Slot index within the page where the record lives
  • nbytes: Size of the record being added/removed
  • data: If add, includes the actual record bytes being inserted

Critical: This record is page-specific. If a replica has a different page layout (e.g., due to earlier splits/merges), it cannot blindly replay __db_addrem. The replicant may need to navigate to the same logical position differently. This is why logical transaction wrappers (schema changes) exist — they're layout-independent.

__bam_split (B-tree Page Split)

Rectype: 3062

When a B-tree page becomes full, split it into left and right pages. Records the split operation.

  • left / right: Page IDs of left and right children
  • indx: Index of the split point
  • root_pgno: Root page of the tree

__bam_rsplit (B-tree Reverse Split)

Rectype: 3063

Opposite of split: merge pages back together when they become too sparse.

__bam_cdel (B-tree Cursor Delete)

Rectype: 3057

Mark a record as deleted without immediately removing it (logical delete for MVCC).

__bam_repl (B-tree Record Replace)

Rectype: 3058

Replace a record in place (used for UPDATE operations that don't change key).

File Operation Records

__fop_create (Create File)

Rectype: 2143

Begin physical file creation.

  • name: Temporary filename (e.g., __db.1.abc)
  • mode: File permissions (e.g., 0666)

__fop_write (Write File)

Rectype: 2145

Write page data to a file (during initial file setup).

  • pgsize: Page size (typically 4096 bytes)
  • pageno / offset: Which page and byte offset
  • page: The actual page data (hex dump)

__fop_rename (Rename File)

Rectype: 2146

Rename temporary file to permanent name (atomic creation).

Registry Records

__dbreg_register (Database Registration)

Rectype: 2002

Maps a physical file to a logical fileid. Essential for recovery — tells the system which files to open.

  • opcode: 1 = OPEN (first reference), 2 = CLOSE, 3 = RE-OPEN
  • name: File path (e.g., XXX.sqlite_stat1_000000.datas0)
  • uid: Unique identifier (40 hex chars, matches pagelist UID)
  • fileid: Assigned logical ID

__db_debug (Debug/Marker Record)

Rectype: 2047

Internal marker. Often contains op codes like 0x02 (new master), used during replication and recovery.

Comdb2-Specific (CUSTOM) Records

CUSTOM: start (Logical Transaction Start)

Rectype: 10006

Begins a logical (schema change) transaction.

  • tranid: Logical transaction ID (used for deduplication)

CUSTOM: commit (Logical Transaction Commit)

Rectype: 10005

Commits a logical transaction.

CUSTOM: add_blkseq (Add Block Sequence)

Rectype: 10019

Record a block sequence identifier for deduplication of logical operations across replicas.

scdone (Schema Change Done)

Rectype: 10002

Marks completion of a schema change operation (table create, alter, etc.).

  • type: Operation type (e.g., 1 = table DDL)
  • table: Table name affected

🔄 Transaction Lifecycle

Anatomy of a User Transaction

BEGIN ↓ User issues: INSERT, UPDATE, DELETE ↓ For each change: - Log __db_addrem (or __bam_* for btree ops) - Modify page in memory buffer pool - prevlsn points to previous record in transaction ↓ User issues: COMMIT ↓ Log __txn_regop_gen_endianize (or __txn_regop_gen) ↓ Flush log to disk (durability point) ↓ Return success to client ↓ Later: Checkpoint includes this transaction, allowing log truncation beyond this point

Transaction ID (txnid)

  • Format: 32-bit hex value (e.g., 0x80000001 = 2147483649)
  • Range: 0x80000000 to 0xFFFFFFFF (starts at 2^31 by convention)
  • Recycled: After checkpoint, __txn_recycle resets the range to allow reuse
  • Unique Transaction ID (utxnid): Monotonically incrementing, never recycled. Useful for ordering across recycles
  • System txnids: txnid=0 for non-transactional records (checkpoints, registry updates, debug markers)

Parent-Child Transactions

Comdb2 uses nested transactions for table creation and schema changes:

Parent txn (80000004) creates a table via:

  1. Child txn (80000005) creates data file 5
  2. Child txn (80000006) creates data file 6
  3. Child txn (80000007) creates index file 7
  4. ... more children for more files ...
  5. Parent txn commits, all children implicitly commit

Benefits: Atomicity — either all files are created or none. If parent aborts, all children abort.

Logical Transactions (Schema Changes)

Comdb2 distinguishes between physical transactions (database engine operations like page splits) and logical transactions (user-visible schema changes). Logical transactions are critical for replication deduplication.

Why logical transactions?

  • Physical transactions at the master might produce different log records on the replicant due to page layout differences
  • A schema change like CREATE TABLE generates many physical transactions (file creates, writes, metadata updates)
  • If the master crashes mid-schema-change and comes back up, it re-sends the same logical operation
  • Without deduplication, replicas would apply it twice — corrupting the schema
  • Solution: Wrap logical operations in a tranid (logical transaction ID). Replicas remember seen tranids and skip duplicates

Logical txn to create a table (on master):

  • CUSTOM: start (begins logical txn, assigns tranid=12345)
  • Physical txn: __fop_create, __fop_write, ... (creates data file 10)
  • Physical txn: __fop_create, __fop_write, ... (creates index file 11)
  • Physical txn: updates comdb2_metadata with schema info
  • CUSTOM: add_blkseq (record dedup key: tranid + blkseq)
  • CUSTOM: commit (end logical txn)
  • scdone (schema change complete)

Replication deduplication logic:

  • Master ships logical txn records to replicas
  • Replicas see CUSTOM: start with tranid=12345
  • Replicas check: "Have I seen tranid 12345 before?"
  • If yes, skip all records until CUSTOM: commit
  • If no, apply all physical operations and record tranid=12345 as seen
  • If master crashes and re-sends, replica skips it (already applied)

💾 Checkpoints & Recovery

Checkpoint Purpose

  • Durability guarantee: All pages modified up to checkpoint are on disk
  • Log truncation: Records before checkpoint can be deleted (no longer needed for recovery)
  • Recovery optimization: Start replay from checkpoint, not from beginning of log
  • Consistency point: Master designates the most recent stable state

Checkpoint Lifecycle

1. Identify all dirty pages (modified since last checkpoint) ↓ 2. Flush all dirty pages to disk (Pages must be persisted before checkpoint record is written) ↓ 3. Write __txn_ckp record with: - ckp_lsn: LSN of oldest active txn - last_ckp: Previous checkpoint LSN - rep_gen: Current replication generation ↓ 4. Flush the checkpoint record to disk (durability point) ↓ 5. Log records before ckp_lsn can now be deleted (old log files recycled) Recovery only needs to replay from ckp_lsn forward

When Do Checkpoints Happen?

  • Automatic periodic: Default ~60 seconds when node is active master with dirty pages
  • On master election: Step-down checkpoint, then new-master checkpoint (rep_gen increments by 2)
  • On recovery: Write __txn_ckp_recovery to mark end of log replay
  • Manual: Admin can force checkpoint (less common)

Recovery Process

When a node crashes and restarts, the recovery process rebuilds a consistent database state from the log:

System crash occurs ↓ 1. ANALYSIS PHASE: - Find last checkpoint record (__txn_ckp) - Scan log from that checkpoint's ckp_lsn forward to current end - Identify: a. "Dirty page set" — all pages modified after ckp_lsn b. "Uncommitted txn set" — all txns that didn't commit before crash - This phase determines what needs to be redone and undone ↓ 2. REDO PHASE: - Replay ALL records from ckp_lsn forward (both committed and uncommitted) - For each __db_addrem, __bam_* record: • Reapply the change to memory (rebuild pages to crash state) • Re-link the page into B-tree structure - Purpose: Restore all changes that were in memory but not yet flushed before crash ↓ 3. UNDO PHASE: - Walk uncommitted transactions BACKWARD in LSN order (reverse transaction order) - For each modification in an uncommitted txn, generate a COMPENSATING RECORD - Example: if __db_addrem with opcode=ADD appears in txn, write __db_addrem with opcode=REMOVE - Write compensating records to WAL (for crash during UNDO) - Purpose: Erase all uncommitted work, leaving only durable committed state ↓ 4. Write __txn_ckp_recovery - Marks that recovery completed successfully - Includes LSN of last undo record for next recovery to skip ↓ 5. Database is consistent and ready for queries

Why Redo Before Undo?

  • Correctness: Redo replays all changes (committed and uncommitted) to rebuild memory state from before crash. Undo then erases only uncommitted work, leaving a clean committed state. Simple undo-only schemes lose durable data; redo-only schemes leave uncommitted garbage
  • Efficiency: Checkpoints mark "already durable" points. Recovery only replays from checkpoint forward, not from log beginning
  • Nested transactions: Parent-child transaction chains use prevlsn links to undo correctly in reverse order

pagelist File (Recovery Optimization)

At checkpoint time, Comdb2 writes a pagelist file listing which pages were dirty:

Format: <fileid> <uid_hex> <page_numbers...> Example: 1 3d8fe001... 0 1 2 3 4 2 fb288a0a... 0 1 Benefit: - Recovery doesn't need to scan entire log - Just process the dirty pages listed here - Much faster for large logs with little activity

🔁 Replication Generations (rep_gen)

What is rep_gen?

Replication generation is a logical clock that increments every time a master election occurs. It helps detect which node is the current master and coordinate replicas.

Master Election Flow

Node A (current master, rep_gen=50) ↓ Network partition / crash ↓ Node B detects master is down, wins election ↓ Node B transitions: - Write checkpoint with rep_gen=50 (step-down checkpoint) - Transition to master state - Write checkpoint with rep_gen=51 (step-up checkpoint; rep_gen increments by 1) ↓ Remaining nodes replicate from Node B (rep_gen=51) - All transactions committed under rep_gen=51 are tagged with generation=51 ↓ If Node B crashes and loses to Node C: Node C writes step-down checkpoint (rep_gen=51) Node C transitions to master Node C writes step-up checkpoint (rep_gen=52)

Rep Gen in Log Records

Every checkpoint and many transaction records include rep_gen:

__txn_ckp on becoming master:

rep_gen: 68      # This node is rep_gen 68 master

__txn_regop_gen during normal operation:

generation: 68   # Transaction committed under rep_gen 68

Using rep_gen for Recovery

  • If a replica receives log records with rep_gen=70 but is at rep_gen=68, it knows the master changed
  • Replicas must not commit transactions from older generations (they might be rolled back in another cluster branch)
  • A new master at rep_gen=71 sends all records tagged rep_gen=71, replicas apply those safely

📄 The pagelist File

Purpose & Location

The pagelist file (located in the same directory as log files) is written at checkpoint time to optimize crash recovery.

Format

<fileid> <uid> <page_numbers...> Example: 1 3d8fe0010f000001edc54c66ddb31800 0 1 2 3 4 2 fb288a0a0f000001684ef369f4e11e00 0 1 3 438fe0010f000001edc54c665dce1e00 0 1 ... Fields: - fileid: Internal file ID (assigned by __dbreg_register) - uid: 40-character hex UID (matches __dbreg_register uid field) - page_numbers: Space-separated list of pages that were dirty

Recovery Using pagelist

  • Without pagelist: Replay entire log from checkpoint, process every record
  • With pagelist: Only process records affecting the listed dirty pages — much faster

Example: If pagelist shows file 39 has pages [0, 1] dirty:

  • Recovery skips all __db_addrem records for files 1-38
  • Only processes records modifying file 39 pages 0-1
  • Large log files can be skipped entirely if not listed

Lifecycle

  • Written at checkpoint: Captures current dirty page set
  • Read at recovery: Used to optimize page replay
  • Discarded after recovery: New pagelist written at next checkpoint

🗂️ File Operations (FOPs)

File operations (__fop_*) create, write, and rename physical data files. They follow a strict order for atomicity.

File Creation Pattern

1. __fop_create - Create temporary file: __db.1.abc - mode: 666 ↓ 2. __fop_write (possibly multiple times) - Write page 0 (metadata page) - Write page 1 (first data page) - etc. ↓ 3. __fop_rename - Rename __db.1.abc → XXX.sqlite_stat1_00000.datas0 - Atomic: Either fully renamed or not at all

Why This Pattern?

  • Atomicity: If crash during FOP, can retry or clean up temp files
  • Crash safety: Rename is atomic on most filesystems — file either exists at new name or old name, never partially
  • Logging: Each step is logged for recovery — can replay file creation even after crash

Transaction Wrapping

FOPs are typically wrapped in a transaction:

txnid 80000005:

  • [1][10324] __fop_create (prevlsn [0][0])
  • [1][10384] __fop_write (prevlsn [1][10324])
  • [1][43228] __fop_write (prevlsn [1][10384])
  • [1][76072] __fop_rename (prevlsn [1][43228])
  • [1][76197] __txn_child → parent 80000004
  • [1][76253] __dbreg_register (prevlsn [1][76197])
  • [1][76378] __txn_regop (commit, prevlsn [1][76253])

If any step fails, parent transaction aborts and all FOPs roll back.

🌳 B-tree Operations

B-tree operations modify the structure of indexes and data pages. They're carefully logged for crash recovery.

Common B-tree Operations

Operation Rectype Purpose
__bam_split 3062 Page became full; split into left/right children. Records old root and new children.
__bam_rsplit 3063 Page became sparse; merge with sibling. Rebalances tree.
__bam_cdel 3057 Cursor delete — mark record as logically deleted without removing immediately (for MVCC).
__bam_repl 3058 Replace record in place. Used for UPDATE where key doesn't change.
__db_addrem 3041 Add or remove record from page (building blocks for other ops).

B-tree Page Split Example

Before: ┌──────────────────────────────────┐ │ Page 1 (ROOT) │ │ Keys: [10, 20, 30, 40, ...full] │ └──────────────────────────────────┘ Insertion of key 25 triggers split: ↓ Log __bam_split record: - left: 2 - right: 3 - indx: 2 (split point) ↓ After: ┌──────────────────┐ │ Page 1 (ROOT) │ │ [20 | 30] │ (now points to children) └─────┬──────┬─────┘ │ │ ┌────┴────┐ ┌──────────┐ │ Page 2 │ │ Page 3 │ │[10,20] │ │[30,40] │ └──────────┘ └──────────┘ During recovery: Replay __bam_split to restore tree structure

MVCC and Logical Deletes

  • DELETE doesn't immediately remove records (would require page reorganization)
  • Instead, __bam_cdel marks the record with a "deleted" flag
  • Readers at older snapshots still see the record; newer readers skip it
  • Periodically, vacuuming removes fully-dead records (committed delete + no active readers)

Summary: The Big Picture

WAL Guarantees Durability

All changes are logged before applied. On crash, replay log from last checkpoint to recover.

LSNs Chain Records Chronologically

Each record points to its predecessor (prevlsn), enabling efficient log replay and transaction rollback.

Checkpoints Enable Optimization

Mark stable points on disk; truncate old log. Recovery starts from checkpoint, not log beginning.

Rep Gens Coordinate Replication

Master elections increment rep_gen. Replicas use it to detect cluster topology changes and avoid conflicts.

Physical Logging + Logical Records

Low-level B-tree ops are physical (page-level); schema/row ops are logical (intent-based) for flexibility.

Transactions Ensure Consistency

Parent-child nesting, logical transactions, and UNDO phase on recovery maintain ACID properties.
