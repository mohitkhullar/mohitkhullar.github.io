Life of an Expert Mode Query in Comdb2

How Comdb2 analyzes your SQL and recommends optimal indexes

cdb2sql>SET EXPERT ON
cdb2sql>SELECT name, balance FROM accounts WHERE id = 42 AND status > 0
Expert mode intercepts SQL queries and runs them through a virtual index analysis pipeline — no data is modified, no query is actually executed against user data. It returns CREATE INDEX recommendations.

Activate — Client1 / 10

SET EXPERT ON

The user activates expert mode for the current session. All subsequent SQL statements will be analyzed for index recommendations instead of being executed.

The client sends SET EXPERT ON (or SET EXPERT FAST for a quicker analysis without full statistics). The server's newsql handler in newsql.c parses this and sets flags on the client state:

clnt->is_expert = 1 — enables expert mode

clnt->is_fast_expert — set if FAST was specified (skips data sampling)

To disable: SET EXPERT OFF clears the flag and returns to normal query execution.

No data is modified. Expert mode is purely analytical. It never executes the user's SQL against actual data. It only analyzes the query structure to recommend indexes that would improve performance.
Activate — Server Dispatch2 / 10

Intercept & Redirect to Expert Handler

When the user submits a SQL query with expert mode active, the server bypasses normal execution and routes to handle_expert_query() instead.

In sqlinterfaces.c, when clnt->is_expert is set, the server calls handle_expert_query() instead of the normal SQL execution path. This function:

1. Downgrades the transaction level if needed (MODSNAP → SOSQL)

2. Prepares the SQL engine with sqlengine_prepare_engine()

3. Hands off to the sqlite3expert analysis pipeline

The user's SQL never reaches the normal query planner or execution engine — it takes a completely separate path designed for index analysis.

Setup — Virtual Databases3 / 10

Create Analysis Databases

sqlite3_expert_new() creates three in-memory SQLite databases that form the expert mode analysis sandbox.

Three databases are created, each with a distinct role:

db — the user's actual database connection (read-only reference for schema and statistics)

dbv — the virtual table database. The user's tables are recreated as virtual tables backed by the expert module. When the query planner runs against these virtual tables, the expert module's BestIndex callback intercepts the planner's requests, capturing exactly what constraints and orderings the planner wants.

dbm — the candidate index database. Tables are recreated as temp tables here, and candidate indexes are added to test whether they improve the query plan.

The schema is copied from the user's real database into both dbv and dbm, with Comdb2-specific transformations (e.g., COLLATE DATACOPY → INCLUDE ALL).

Setup — Statement Registration4 / 10

Register SQL for Analysis

sqlite3_expert_sql() parses the user's SQL statement and adds it to the analysis queue.

The SQL statement is parsed and validated against the dbv virtual table database. If it parses successfully, it is stored in a linked list of IdxStatement objects for analysis.

Each IdxStatement captures:

zSql — the original SQL text

zIdx — (populated later) the recommended indexes for this statement

zEQP — (populated later) the EXPLAIN QUERY PLAN output with recommended indexes

Multiple statements can be registered for batch analysis, though typically expert mode processes one query at a time.

Analysis — Constraint Extraction5 / 10

Capture Planner Constraints via Virtual Tables

The query is executed against the virtual tables in dbv. The expert module's BestIndex callback intercepts the planner, capturing every constraint and ORDER BY the planner requests.

This is the key insight of expert mode's design. When SQLite's query planner runs against the virtual tables, it calls expertBestIndex() for each table scan. This callback:

1. Extracts all WHERE clause constraints — equality (=), range (>, <, ≥, ≤), and IS NOT NULL

2. Extracts ORDER BY column requirements

3. Creates IdxScan objects recording exactly what the planner needs

4. Filters non-indexable column types via comdb2_is_field_indexable() — skipping BLOB, BYTEARRAY, VUTF8, and other types that can't be indexed in Comdb2

The result is a precise map of what the query planner wishes it had for optimal execution.

Analysis — Candidate Generation6 / 10

Generate Candidate Indexes

idxCreateFromWhere() combines the captured constraints into candidate index definitions and creates them as temp indexes in dbm.

For each captured scan, the algorithm generates candidate indexes by combining:

Equality constraints first — all = columns go into the index prefix (order doesn't matter for equality)

Then each range constraint — each >, < column is tried individually after the equality columns

Then ORDER BY columns — appended to potentially enable index-ordered scans

For our query WHERE id = 42 AND status > 0, candidates might include: (id), (id, status), (status), and (status, id).

idxFindCompatible() checks whether an existing index already covers a candidate, avoiding redundant recommendations. Each surviving candidate is created as a CREATE TEMP INDEX in dbm with a hash-based name like accounts_idx_00000069.

Analysis — Statistics7 / 10

Populate Index Statistics skipped in FAST mode

idxPopulateStat1() runs ANALYZEEXPERT on the candidate indexes to generate cardinality statistics in sqlite_stat1.

For the query planner to make accurate cost estimates, it needs to know the cardinality (selectivity) of each candidate index. This stage:

1. Runs ANALYZEEXPERT (a Comdb2-specific variant of ANALYZE) on each candidate index in dbm

2. Samples the actual table data using configurable percentage-based sampling

3. Populates sqlite_stat1 with rows like 16 1 (16 total rows, 1 row per distinct index value — meaning perfectly selective)

The planner uses these statistics in the next stage to decide which candidate index actually gives the best plan.

FAST mode skips this. SET EXPERT FAST sets iSample = 0, bypassing all data sampling. This is much quicker but the planner works without cardinality data, so recommendations may be less optimal. Useful for quick exploratory analysis.
Evaluation — Plan Comparison8 / 10

Run EXPLAIN QUERY PLAN with Candidates

idxFindIndexes() runs EXPLAIN QUERY PLAN for each statement against dbm, which now has all candidate indexes available.

This is where the planner gets to "try on" the candidate indexes. For each registered SQL statement:

1. EXPLAIN QUERY PLAN is executed against dbm (which has the temp candidate indexes)

2. The EQP output is parsed for USING INDEX or USING COVERING INDEX references

3. If the planner chose a candidate index, that index is marked as recommended

4. If the planner didn't use any candidate (e.g., an existing index was already optimal), no recommendation is made

The planner applies the same cost-based optimization it uses for real queries — but now it has the candidate indexes available. The indexes it actually selects are the ones worth creating.

Evaluation — Report Generation9 / 10

Build Recommendation Report

sqlite3_expert_report() collects the recommended indexes, their statistics, and the improved query plans into the final output.

The report system supports four output types via EXPERT_REPORT_* constants:

EXPERT_REPORT_SQL — the original SQL statement text

EXPERT_REPORT_INDEXES — CREATE INDEX statements for the recommended indexes for this query

EXPERT_REPORT_PLAN — the EXPLAIN QUERY PLAN output showing how the query would use the recommended indexes

EXPERT_REPORT_CANDIDATES — all candidate indexes that were tested, with their stat1 data

The server uses EXPERT_REPORT_CANDIDATES to return the full set of tested candidates, giving the user visibility into what was considered and why.

Result — Recommendation10 / 10

Return Index Recommendations

The recommended CREATE INDEX statements are sent back to the client via the standard protobuf response channel.

The server calls write_response() to send the recommendations back to the client through the normal newsql protobuf wire protocol. The user sees output like:

---------- Recommended Indexes ---------- CREATE INDEX accounts_idx_00000069 ON accounts(id, status); -- stat1: 1000 1 50 ------------------------------------------

The stat1 comment shows the cardinality data: total rows, then rows per distinct value for each index column. Lower numbers mean higher selectivity (better).

After the response, sqlite3_expert_destroy() cleans up all three analysis databases (db, dbv, dbm) and frees all allocated structures. The user can then decide whether to actually create the recommended index.
