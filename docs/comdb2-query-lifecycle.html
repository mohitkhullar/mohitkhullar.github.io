Client — cdb2api1 / 16

Application Issues Query

The application calls the client library with a SQL statement and optional bound parameters to begin the query lifecycle.

Using cdb2api, the application calls cdb2_run_statement() or cdb2_run_statement_typed() for parameterized queries. The SQL string and any bind variables are captured by the client handle (cdb2_hndl_tp).

Any language works. The Comdb2 wire protocol is defined entirely by protobuf schemas. You can write a client in Python, Java, Go, or any language with protobuf support. cdb2api is the reference C implementation, but it is not required.
Client — Service Discovery2 / 16

Service Discovery

Locate all nodes in the database cluster using a tiered discovery strategy: Consul DNS, comdb2db meta-database, or static configuration.

Consul DNS — SRV record lookup returns a prioritized host list with ports. A records resolve IP addresses. Results are cached with a configurable TTL to avoid repeated lookups.

comdb2db — a meta-database that maintains a registry of all Comdb2 clusters and their current node membership. Used as a fallback when Consul is unavailable.

Config file — a static host list, used as a last resort. A custom protobuf client can also connect directly to a known host, bypassing discovery entirely.

Client — Connection Management3 / 16

Connection & Node Selection

Reuse an idle connection from sockpool, or establish a new TCP connection to the best available node using proximity-aware routing.

cdb2api first checks sockpool for an existing idle connection to reuse, avoiding TCP and SSL handshake overhead. If none is available, a new connection is established.

Node selection uses proximity-based routing — preferring nodes in the same data center or machine room for lowest latency. For reads, any node can serve the query under snapshot isolation. For writes, the client routes to the master, or the connected replicant will forward the request.

Client — Wire Protocol4 / 16

Serialize & Send

The query is packed into a CDB2_SQLQUERY protobuf message and written to the TCP socket as a length-prefixed frame.

SQL text, bind parameters, authentication credentials (username/password or token), and request metadata (flags, timezone, feature negotiation) are serialized per sqlquery.proto. The auth token is included with the request so the server can validate the client's identity before executing the query. The message is length-prefixed and written to the socket in a single framed write.

Protocol buffers = language-agnostic. The sqlquery.proto and sqlresponse.proto schemas fully define the wire format. Any client that can serialize protobuf and open a TCP socket can communicate with Comdb2 — no dependency on cdb2api or C code required.
Network — Transport5 / 16

Network Transport

The protobuf-framed message travels over a persistent TCP connection with optional SSL/TLS encryption to the database node.

The server's accept thread picks up the connection and identifies the newsql protocol. A dedicated appsock handler thread is assigned for this client session.

If SSL/TLS is configured, the handshake completes before any application data is exchanged. The framed protobuf message is read and decoded by newsql_read_request().

Since the protocol is defined by protobuf schemas, the server is entirely agnostic to the client's implementation language — it processes the same protobuf messages regardless of origin.

SQL Engine — Security6 / 16

Authentication & Authorization

Verify client credentials, then enforce table-level and column-level permissions before allowing the query to proceed.

Authentication: The server validates the client's credentials (username/password or certificate-based). Auth results are cached per session to avoid repeated verification on every query.

Authorization: Table-level ACLs are checked: READ, WRITE, or DDL. Column-level permissions restrict which columns a user can access. Row-level security policies can further filter visible data.

Federated queries: For remsql queries spanning multiple clusters, credentials are forwarded to the remote cluster for independent validation — each cluster enforces its own access control.

SQL Engine — Parser7 / 16

SQL Parsing

The SQLite-derived Lemon parser tokenizes the SQL text and produces an abstract syntax tree (AST).

The SQL string is fed into Comdb2's parser, derived from SQLite's parse.y grammar. The tokenizer (tokenize.c) breaks the SQL into tokens, and the Lemon-generated LALR parser produces an AST representing the query structure.

Comdb2 extends the grammar with custom SQL: SELECTV (verified reads for serializable isolation), SET TRANSACTION, EXEC PROCEDURE, CREATE LUA FUNCTION, PUT tunable commands, and more.

Alternate path — Lua Stored Procedures. When the parser encounters EXEC PROCEDURE sp_name(args), it dispatches to the Lua SP engine instead of the cost-based optimizer. A server-side Lua VM executes the procedure, which can contain loops, conditionals, and multiple SQL statements. Each SQL statement inside the SP goes through the full pipeline (parse → plan → VDBE → BerkeleyDB), but all execute within a single server-side transaction — eliminating client round-trips for multi-statement logic.
SQL Engine — Optimizer8 / 16

Query Planning & Optimization

The cost-based optimizer evaluates available indexes, estimates selectivity, and compiles the cheapest plan into VDBE bytecode.

The planner evaluates indexes on accounts and uses stored statistics (sampled histograms) to estimate how many rows match id = 42. If an index on id exists, it picks an index seek (O(log n)) over a full table scan.

The output is a VDBE bytecode program — a sequence of opcodes the execution engine will interpret. SQL fingerprinting caches compiled plans for repeated queries with different bind values, avoiding re-planning overhead.

Execution — Transaction9 / 16

Transaction Begin

Open a transaction at the configured isolation level — snapshot or serializable — establishing an LSN-based point-in-time read view.

Snapshot isolation: provides a consistent point-in-time view of the database. Each page is checked against the transaction's start LSN, ensuring reads always see committed data from that moment — without blocking concurrent writes.

Serializable isolation: extends snapshot with write-write conflict detection. If two concurrent transactions modify the same rows, one is aborted and the client retries automatically.

The transaction acquires an LSN-based read view, pinning which version of each B-tree page is visible for the duration of the query.

Execution — Bytecode10 / 16

VDBE Execution

The VDBE interpreter steps through the compiled bytecode program — opening cursors, seeking into indexes, and fetching matching rows.

The Virtual Database Engine runs opcodes sequentially. For our query:

OpenRead → opens a B-tree cursor on the index for accounts

SeekGE → positions the cursor to the first entry where id ≥ 42

Column → extracts name and balance from the matching row

ResultRow → emits the result row back toward the client

Each data-access opcode calls through Comdb2's backend layer (sqlite3BtreeXxx()) which maps to BerkeleyDB cursor operations.

Stored procedures — Lua orchestrates, VDBE executes. For EXEC PROCEDURE calls, a Lua VM runs the stored procedure server-side. The Lua code orchestrates the logic — loops, conditionals, cursor iteration, result emission — but each SQL statement it executes internally (db:exec(), db:prepare()) goes through the full parse → plan → VDBE → BerkeleyDB pipeline. The key advantage: all statements run within a single server-side transaction, eliminating client round-trips and ensuring atomicity for complex multi-statement operations.
Execution — Storage11 / 16

B-Tree & Buffer Pool

Navigate BerkeleyDB B-trees to locate data. Pages are served from the in-memory buffer pool or read from disk on a cache miss.

Comdb2 uses BerkeleyDB B-trees for both index and data storage:

Index files (.ix0, .ix1, ...) — sorted B-trees for each defined index. The seek for id = 42 traverses from root to leaf page.

Data files (.dta stripes) — contain the actual row payloads, spread across multiple data files for parallelism.

The buffer pool caches frequently accessed pages in memory. A cache hit serves the page in microseconds; a miss triggers a disk read. Ondisk records are converted to the current in-memory schema via vtag_to_ondisk(), enabling live schema changes without downtime.

Execution — Processing12 / 16

Row Filtering & Projection

Apply remaining WHERE predicates not covered by the index, project the requested columns, and enforce any constraints.

After fetching candidate rows from the B-tree, any residual WHERE conditions not fully covered by the chosen index are evaluated as post-fetch filters.

Projection extracts only the requested columns (name, balance), discarding the rest. Type conversion and formatting (datetime zones, decimal precision) are applied here.

For write operations, this stage also enforces constraints: NOT NULL, CHECK, UNIQUE, and foreign key validations.

Replication — Cluster13 / 16

Replication & Commit writes only

For write transactions: generate log records, broadcast to all replicants, and wait for majority acknowledgment before confirming the commit.

Write transactions produce BerkeleyDB log records describing each mutation. Comdb2 uses logical replication — the master broadcasts logical log records (not physical page images) over the replication network to all replicant nodes, allowing replicants to maintain consistency even across independent schema versions.

Durable commits require a majority of nodes to acknowledge receipt before the server returns success. This guarantees the write survives any single node failure.

Master forwarding: if the client connected to a replicant for a write, the replicant transparently forwards the entire transaction to the master for execution and replication. The client does not need to reconnect.

Read queries skip this stage entirely — they are served from any node's local snapshot. Stored procedure transactions also flow through this path — the entire multi-statement SP commits as a single replicated unit.

Replication — High Availability14 / 16

HASQL — Transparent Failover

If the connected node fails mid-query, the client library transparently detects the failure and retries on another healthy node.

HASQL (High Availability SQL) is a protocol between cdb2api and the server that enables transparent failover without application-visible errors.

What triggers failover: The is_retryable() function in cdb2api.c determines which errors trigger automatic retry. The retryable errors are: CDB2ERR_NOMASTER (no master available — also returned by physical replicants that reject writes), CDB2ERR_TRAN_IO_ERROR (I/O failure mid-transaction), CDB2ERR_REJECTED (server too busy), and MASTER_TIMEOUT. Additionally, CHANGENODE (protobuf error 402) is returned on durability failures when a commit could not be made durable across the cluster.

Retry conditions: Retries only happen when there is a snapshot file (SNAPSHOT isolation transaction), or the query is not inside a transaction, or there is a pending commit to verify. The client disconnects, fetches updated cluster info via cdb2_dbinfo(), connects to a different host, and resends all queries from the transaction start. Max retries: num_hosts × 3.

For reads: the client detects the error response or broken connection, picks another node, and re-executes. Safe because reads are served from consistent snapshots.

For writes — the ambiguous failure case: The most critical scenario is when the connection drops after the client sends a commit but before receiving the response. The client attaches a unique transaction ID (uuid) to every write. On retry, it queries another node to check if that uuid was committed. If yes, it returns success without re-executing. If no, it safely retries. This prevents duplicate writes.

Physical replicants: Dedicated read-only physical replicants reject writes with ERR_NOMASTER (via toblock.c). Normal cluster replicants can forward writes to the master. If the master is unreachable or in election, cdb2api retries until a new master is elected.

Response — Serialization15 / 16

Result Streaming

Result rows (or error responses) are packed into CDB2_SQLRESPONSE protobuf messages and streamed back to the client.

Each response message contains either a result row or an error code with context. The response type field tells the client what it's receiving: data rows, last row marker, or an error that may trigger HA retry (see HASQL stage).

For success, column types are encoded per the wire protocol: INTEGER, REAL, CSTRING, BLOB, DATETIME, INTERVALDS, INTERVALYM, and more. Rows are streamed incrementally — the client can start consuming results before the query finishes on the server.

For errors, the response includes the error code (e.g., CDB2ERR_NOMASTER, CDB2ERR_TRAN_IO_ERROR, CHANGENODE) and an error string. The client library's is_retryable() function inspects the error code to decide: return the error to the application, or transparently retry on another node via HASQL.

Any protobuf-capable client can decode these CDB2_SQLRESPONSE messages directly from the wire — the format is fully defined by the proto schema.

Response — Delivery16 / 16

Client Receives Results

The client library delivers decoded rows to the application. When complete, the TCP connection returns to sockpool for reuse by the next query.

The application calls cdb2_next_record() in a loop. Each call decodes the next protobuf response and returns the row. Column values are accessed with cdb2_column_value(), cdb2_column_type(), and cdb2_column_size().

When all rows are consumed, CDB2_OK_DONE signals query completion. The TCP connection is returned to sockpool for reuse, avoiding connection setup overhead on the next query.
