Register — DDL1 / 12

CREATE PROCEDURE

The stored procedure source code is registered and persisted to BerkeleyDB as a schema change, making it available for execution across the cluster.

The SQL CREATE PROCEDURE procname VERSION 'v1' { ... lua source ... } is parsed by comdb2build.c. The parser calls comdb2CreateProcedure() which:

1. Validates authorization (SQLITE_CREATE_PROC permission)

2. Creates a schema change request with kind = SC_ADDSP

3. Persists the Lua source to BerkeleyDB's llmeta tables

Procedures support versioning — either numeric (1, 2, 3) or string-based ('v1.0', 'qa_release'). A default version can be set with PUT DEFAULT PROCEDURE procname 'version'. The schema change replicates to all cluster nodes, making the SP available cluster-wide.

Invoke — Client2 / 12

EXEC PROCEDURE

The client sends EXEC PROCEDURE get_account(42) over the newsql protobuf wire protocol, just like a regular SQL query.

From the client's perspective, executing a stored procedure uses the same path as any SQL statement — cdb2_run_statement() sends the SQL text via protobuf. Service discovery, connection pooling (sockpool), and node selection all work identically.

Arguments are passed as part of the SQL text. The SP can also accept bound parameters via the standard cdb2_bind_param() interface.

HASQL transparent failover applies to stored procedure calls as well — if the node fails, the client retries the entire EXEC PROCEDURE on another node.

Invoke — Server Dispatch3 / 12

Parse & Route to SP Handler

The server's SQL parser recognizes EXEC PROCEDURE and routes execution to exec_procedure() in sp.c, bypassing the normal query planner.

The parser identifies EXEC PROCEDURE as a stored procedure invocation. Instead of going through the cost-based optimizer and VDBE bytecode compilation, the request is handed to exec_procedure() — the main entry point for SP execution in sp.c.

This function extracts the SP name via get_spname() and parses the arguments. It then enters the SP setup and execution pipeline, which is entirely separate from the regular SQL path.

VM Setup — Cache4 / 12

Lua VM Cache Check

setup_sp_int() checks if a cached Lua VM exists for this procedure. If the SP name, version, and lua_version all match, the existing VM is reused.

Comdb2 caches the Lua VM per client connection (clnt->sp). A cache hit requires all of:

1. sp->spname matches the requested procedure

2. sp->spversion (numeric or string) matches the current default version

3. sp->lua_version == gbl_lua_version (a global counter bumped whenever any SP is modified, invalidating all cached VMs)

On a cache hit, the existing VM is reused — skipping source loading and compilation. On a cache miss, a new VM is created from scratch.

VM Setup — Compile5 / 12

Load Source & Compile

On a cache miss, the SP source is loaded from BerkeleyDB and compiled into Lua bytecode via luaL_dostring().

create_sp_int() creates a fresh Lua VM using lua_newstate() with a per-thread memory allocator (mspace). Then:

Load source: load_src() retrieves the Lua source from BerkeleyDB using bdb_get_sp_lua_source() (numeric version) or bdb_get_versioned_sp() (string version). System procedures load from compiled-in sources.

Compile: luaL_dostring(L, src) parses and compiles the Lua source into bytecode. If compilation fails, the error is returned to the client.

Standard Lua libraries are opened via luaL_openlibs(), and an instruction-count hook is installed to enforce execution limits.

VM Setup — API6 / 12

Register Database API

The db module and all Comdb2-specific types are registered into the Lua VM, giving the SP full access to database operations.

Several initialization functions register the SP's database API:

init_db_funcs() — the db global with query, transaction, and utility functions

init_dbstmt_funcs() — prepared statement type (fetch, bind, column_value, emit)

init_dbtable_funcs() — temp table type (insert, emit)

init_dbthread_funcs() — threading API (create_thread, join)

init_dbconsumer_funcs() — queue consumer API (get, poll, consume)

Based on the SP type, functions are selectively added or removed: triggers get add_trigger_funcs() but lose emit and explicit transactions; consumers get add_consumer_funcs().

Execution — Arguments7 / 12

Push Arguments onto Lua Stack

push_args() parses each argument from the EXEC PROCEDURE call and pushes it onto the Lua stack as a typed value.

Arguments from EXEC PROCEDURE get_account(42) are parsed and pushed as Lua values:

Numbers → lua_pushinteger() or lua_pushnumber()

Strings → lua_pushstring()

Blobs → lua_pushlstring() with binary data

Bound parameters → extracted from the protobuf request's bind array

The SP's main() function receives these as its arguments: function main(account_id) ... end. The argument count is tracked so lua_pcall() knows how many values to pop.

Execution — main()8 / 12

Execute main() via lua_pcall

The SP's main() function is called via lua_pcall(). The Lua VM executes the procedure with full access to the database API.

get_func_by_name() retrieves the main function from the Lua global table (or comdb2_trigger_main for triggers). Then:

lua_pcall(lua, argcnt, LUA_MULTRET, 0) executes the SP in protected mode. Any Lua error (runtime error, db:emit failure, constraint violation) is caught and returned to the client.

An instruction count hook fires on every Lua instruction, incrementing sp->num_instructions. If it exceeds sp->max_num_instructions (configurable via db:setmaxinstructions()), the SP is terminated with "Exceeded instruction quota."

During execution, the SP can call db:exec(), db:prepare(), db:emit(), db:begin()/db:commit(), and all other registered API functions.

Execution — SQL Inside SP9 / 12

SQL Statements Go Through Full Pipeline

Each db:exec() or db:prepare() call inside the SP goes through the full SQL pipeline: parse → plan → VDBE → BerkeleyDB.

When the Lua code calls db:exec("SELECT balance FROM accounts WHERE id = ?"), it invokes lua_prepare_sql() which calls into the standard SQLite/Comdb2 SQL engine:

1. Parse — Lemon parser tokenizes and builds the AST

2. Plan — cost-based optimizer selects indexes and generates VDBE bytecode

3. Execute — VDBE interpreter steps through opcodes, accesses BerkeleyDB B-trees

For read statements, a dbstmt handle is returned to Lua for iteration via stmt:fetch(). For write statements (INSERT/UPDATE/DELETE), the statement is auto-stepped to completion and the rows-changed count is available via stmt:rows_changed().

All statements execute within the SP's transaction context — they see the same snapshot and their writes are part of the same atomic unit.

Results — Transactions10 / 12

Transaction Semantics

The SP can explicitly manage transactions with db:begin(), db:commit(), and db:rollback(), or run within an implicit parent transaction.

Transaction control follows a state machine: NORMAL → PRE_STRT → INTRANS → FNSH → NORMAL.

Explicit transactions: The SP calls db:begin() to start, executes multiple SQL statements, then db:commit() or db:rollback(). All statements between begin and commit are atomic.

Commit with effects: db:commit({with_effects=true}) returns a table with num_affected, num_selected, num_inserted, num_updated, num_deleted — giving the SP visibility into what the transaction did.

Error rollback: If the SP throws an uncaught error while a transaction is active, db_rollback_int() automatically aborts the transaction before returning the error to the client.

On commit, the write path is the same as for regular queries: log records are generated, replicated to the cluster, and the commit waits for majority ack.

Results — Emission11 / 12

Result Emission via db:emit()

The SP sends result rows back to the client by calling db:emit(). Results are streamed incrementally as they are produced.

db:emit() is polymorphic — it handles multiple input types:

Individual values: db:emit(name, balance) → sends one row with positional columns

Lua table: db:emit({name="Alice", balance=10042.50}) → sends one row with named columns

dbstmt: stmt:emit() → streams all result rows from a prepared statement

dbtable: tbl:emit() → sends all rows from a temp table

Column metadata is set via db:column_name() and db:column_type() before the first emit. Internally, l_send_back_row() serializes the row and calls write_response(clnt, RESPONSE_ROW, ...) to stream it over the protobuf wire protocol. The client receives rows via the normal cdb2_next_record() loop.

db:emiterror(msg) sends an error message to the client without terminating the SP.

Cleanup — Finalize12 / 12

Cleanup & Finalize

After main() returns, the SP's return value is processed, resources are cleaned up, and the final response is sent to the client.

Return value: emit_result() inspects what main() returned on the Lua stack — a number becomes a return code (range -299 to -200), a string becomes an error message, a table is emitted as additional result rows.

Transaction check: commit_sp() verifies all transactions were properly terminated. An open transaction at SP exit is an error.

Flush: flush_sp() sends RESPONSE_ROW_LAST to signal the client that all rows have been sent.

Resource cleanup:

• reset_sp() — resets SP state for potential VM reuse on the next call

• lua_gc(L, LUA_GCCOLLECT, 0) — runs a full Lua garbage collection cycle

• drop_temp_tables() — deletes any temporary tables created by the SP

• free_tmptbls() — frees temp table tracking structures

The Lua VM is not destroyed — it is cached on clnt->sp for reuse if the same SP is called again on this connection.
